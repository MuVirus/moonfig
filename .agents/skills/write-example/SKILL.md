# 示例撰写规范

示例的职责是**最小可运行地证明一个点**，不是功能巡礼。读者打开示例，应先看到“在调用什么”，而不是构建系统或展示代码。

每写一句注释、一段代码前先问：**读完它，读者能多做对一件事吗？删掉它，读者会做错吗？** 两个答案都是“否”，就删掉。

## 一、主题

- 一个示例只证明一个点，目录名就是主题。
- 同一能力只在一个示例里演示一次，其他示例用链接指过去。
- 输入控制在 1 个成功 + 最多 1 个相关失败。
- 与主题无关的场景删掉，不要为了“全面”堆输入。

## 二、结构

- 一个可运行入口，一个 README。
- 入口只保留证明主题所需的类型、配置和调用。
- 测试、基准、辅助脚本不放进示例目录。
- 示例必须能直接运行到结束，不依赖交互输入。

## 三、代码

- 核心调用要在前三屏出现，不要被包装函数或展示逻辑藏起来。
- 多个输入只保留差异明显的一份基础配置，再覆盖变化的字段；不要复制多份近似内容。
- 输出直接读字段，不要为打印另写一层 helper。
- 错误只在最外层处理一次；预期失败只处理那一次调用，并标注。
- 命名按含义，不要用缩写或首字母区分多个变量。

## 四、注释

注释只回答两个问题：

- 这行在调用什么？
- 这个字段对应配置里的哪个键？

不要写：

- 构建、生成、发布步骤
- 库的内部设计或架构宣言
- 语言或标准库的历史包袱
- 仓库策略
- 对预期输出的逐条复述

示例自身需要的脚手架可以保留，但要标出来，并压到最短。

## 五、README

固定四段，控制在 60 行内：

1. 一句话主题
2. 运行命令
3. 关键片段（5–10 行，其余链接到入口文件）
4. 真实输出

不要整段复制源码，不要写“入口列表”“和 X 怎么选”“边界”“设计取舍”等手册内容；这些放文档，示例里用链接。

## 六、完成前检查

- [ ] 十秒内能找到核心调用
- [ ] 只有一个主题，其他主题已删除或改成链接
- [ ] 输入不超过 2 个，差异一眼可见
- [ ] 没有为输出另写的 helper
- [ ] 错误只在一层处理
- [ ] 注释只解释调用和键名
- [ ] README 没有复制源码
- [ ] 实际运行输出与 README 一致
- [ ] 格式化和检查通过
